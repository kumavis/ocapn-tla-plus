# Wire-level reference for path-change protocols, intra-vat queue cascade, and 3PHO

This note is the **wire-level protocol reference** for
[`spec/PromiseResolution.tla`](../spec/PromiseResolution.tla). For the
path-change taxonomy (promise resolution vs promise shortening) and the
tracked future-work items that hang off it, see
[`path-changes.md`](path-changes.md). For the precise per-variable
locality contract every protocol action is required to satisfy — what
each peer is allowed to read and write — see
[`locality-contract.md`](locality-contract.md). This note is the
source of truth for wire shapes; the others are the source of truth
for definitions and for the implementability contract.

## Vocabulary

- **path change** — any event that changes the network route a future
  send on a ref will take. Covers both flavours below. The umbrella
  term in [`path-changes.md`](path-changes.md).
- **promise resolution** — a `LocalPromise` resolves to a `Target`
  (`LocalTarget` or `RemoteTarget`). Propagated on the wire by
  `op:resolve(refId, desc:remote-target(...))`.
- **intra-vat promise shortening** — a `LocalPromise` at peer `H`
  resolves to another ref *also hosted at* `H`; `H` drains the
  resolving promise's queue directly into the new ref. **No wire
  traffic** is generated by the shortening itself.
- **distributed (inter-vat) promise shortening** — a `LocalPromise`
  resolves to a `Promise` on a different vat; listeners would learn
  this via a (currently unimplemented) `desc:remote-promise` variant
  of `op:resolve` and shorten their own dispatch through the new
  promise's host. The `RemotePromise.localResolution` slot is in the
  spec as the substrate for this, but no action writes a
  promise-to-promise resolution today. See
  [`path-changes.md`](path-changes.md) §1.2.b and §3.1 for the work
  item.
- **terminal-only resolution propagation** — `op:resolve(targetRefId,
  value)` is sent to a listener *only* when `value` denotes a `Target`.
  When the resolution is to a `Promise`, listeners stay on their
  `RemotePromise` route; the resolver keeps forwarding through its
  own queue / intra-vat cascade machinery.

## 1. Reference taxonomy

```
Reference        = Promise | Target
Promise          = LocalPromise | RemotePromise
Target           = LocalTarget | RemoteTarget
RemoteReference  = RemotePromise | RemoteTarget
LocalReference   = LocalPromise | LocalTarget
```

Each peer maintains a partial map `vats[p].refs[refId] = entry`. The
entry's `kind` field discriminates the four cases:

| `kind`          | Fields                                                                |
| --------------- | --------------------------------------------------------------------- |
| `LocalTarget`   | `sink` — the message sink (delivered log in our model)                |
| `RemoteTarget`  | `targetPeer`, `targetRefId`                                           |
| `LocalPromise`  | `queue`, `listeners`, `resolution` (`<none>` or a `Reference`)        |
| `RemotePromise` | `resolverPeer`, `resolverRefId`, `localResolution` (`<none>` or ref)  |

### Pairing invariant — every remote ref has a local presence

Every `RemoteX` on peer A is the local-side presence of a corresponding
`LocalX` on the peer whose name it carries. Quantified over the *allocated*
domain `DOMrefs(p) = {r : vats[p].refs[r] # EntryNone}` only:

```tla
PairingInvariant ==
    /\ \A p \in Peers, r \in DOMrefs(p) :
         vats[p].refs[r].kind = "RemoteTarget" =>
            LET q == vats[p].refs[r].targetPeer
                rq == vats[p].refs[r].targetRefId
            IN rq \in DOMrefs(q) /\ vats[q].refs[rq].kind = "LocalTarget"
    /\ \A p \in Peers, r \in DOMrefs(p) :
         vats[p].refs[r].kind = "RemotePromise" =>
            LET q == vats[p].refs[r].resolverPeer
                rq == vats[p].refs[r].resolverRefId
            IN rq \in DOMrefs(q) /\ vats[q].refs[rq].kind = "LocalPromise"
```

A single `Local*` entry on peer `q` may be the presence of many `Remote*`
entries across other peers — that's the natural many-to-one shape of a
capability with many holders. The invariant is preserved by every
action that mints a new ref entry (`Init` and the 3PHO actions).

### refId namespacing (v0 convention)

The model uses **globally-unique refIds shared across peers**: a
single integer `r` identifies the same logical capability
everywhere it appears. Both the resolver-side `LocalPromise` and a
holder's `RemotePromise` use the same `r`; both the target host's
`LocalTarget` and any holder's `RemoteTarget` use the same `r`. This
keeps `op:resolve(targetRefId, value)` trivially well-defined and matches
the existing chain models' shared `ChainRefs` convention.

Real OCapN uses per-peer (per-session) refId namespaces: each peer
maintains its own import/export tables, and messages reference refIds in
the destination peer's namespace. `op:listen(subscriberRefId,
resolverRefId)` would carry both sides' refIds so the resolver knows
which answer-position to address its `op:resolve` to. Translating the v0
model to per-peer namespaces is a mechanical change and is out of scope
here.

### `LocalPromise.resolution` vs `RemotePromise.localResolution`

These are deliberately different fields and the names should not be
conflated:

- `LocalPromise.resolution` — the promise's **actual resolution**, set
  by `ResolverResolve` at the resolver peer. Once non-`<none>`, the
  promise *is* that ref. Drives intra-vat queue cascade at the
  resolver and listener notification.
- `RemotePromise.localResolution` — what the *holder* has **learned
  about** the promise's resolution, via `op:resolve`. Once non-`<none>`,
  the holder routes future sends directly through the new ref
  (subject to flush-protocol gating). The remote
  `LocalPromise.resolution` may have been set well before any holder's
  `localResolution` catches up.

## 2. Sending semantics (single dispatch)

When peer `self` is asked to send `m` via refId `r`:

| `vats[self].refs[r].kind`           | Action                                          |
| ----------------------------------- | ----------------------------------------------- |
| `LocalTarget`                       | apply `m` to `entry.sink` (deliver)             |
| `RemoteTarget`                      | append `op:deliver-only(...)` to `channels[self][entry.targetPeer]` |
| `LocalPromise` (unresolved)         | append `m` to `entry.queue`                     |
| `LocalPromise` (resolved)           | recurse on `entry.resolution` (send-time recursion through resolved promise) |
| `RemotePromise` (no localResolution)| append `op:deliver-only` to `channels[self][entry.resolverPeer]` |
| `RemotePromise` (with localResolution) | recurse on `entry.localResolution`           |

## 3. Intra-vat promise shortening (queue cascade)

When a `LocalPromise pa` at peer `H` becomes resolved to `R'`, and
`R'` is hosted at the *same* `H`:

- If `R'.kind = LocalTarget`: each `m \in pa.queue` is applied to
  `R'.sink` (delivered).
- If `R'.kind = LocalPromise pb`: append `pa.queue` into `pb.queue`.
  (`pb` may itself be resolved → recurse: the **queue cascade** runs
  entirely inside `H`.)

No wire traffic generated by the shortening itself. This is the only
form of promise-to-promise shortening modelled; inter-vat (distributed)
promise shortening is tracked in [`path-changes.md`](path-changes.md)
§1.2.b.

If `R'` is a remote ref (`RemoteTarget` / `RemotePromise`), the queue
is drained over the wire to `R'`'s peer (same as today's
`ProcessPending`).

## 4. Terminal-only resolution propagation

When a `LocalPromise pa` at `H` becomes resolved to `R'`:

| `R'.kind`              | Notify listeners?                              | 3PHO? |
| ---------------------- | ---------------------------------------------- | ----- |
| `LocalTarget`          | Yes — `op:resolve(targetRefId, desc:remote-target(H, R'_local))` per listener | No — listener already has session with `H` |
| `RemoteTarget`         | Yes — `op:resolve(targetRefId, desc:handoff-give(...))` per listener | **Yes** — listener has no session with `R'.targetPeer` |
| `LocalPromise`         | **No** — silent; listeners stay on their `RemotePromise` to `H`; `H` drains `pa.queue` into `R'.queue` (intra-vat cascade) | n/a |
| `RemotePromise`        | **No** — silent; listeners stay on their `RemotePromise` to `H`; `H` drains `pa.queue` over the wire to `R'.resolverPeer` | n/a |

Listeners that receive `op:resolve` do **not** further propagate. They
never `op:listen` on the new ref and never send `op:resolve` to their
own listeners. That's the deferred inter-vat distributed promise
shortening — see [`path-changes.md`](path-changes.md) §1.2.b / §3.1.

Rule of thumb: an `op:resolve` is sent iff the resolution introduces the
listener to a *terminal* capability (`Target`). When `R'` is a peer the
listener already knows (`LocalTarget` on `H`), the bypass uses a plain
`desc:remote-target`; when `R'` is a third peer, 3PHO is required.

## 5. Wire messages and descriptors

**Messages** (travel on `channels[from][to]` and consume FIFO slots):

```
op:deliver-only(sender, sentOnRef, seq, pos)
op:resolve(targetRefId, value)
op:listen(subscriber, refId)
op:deposit-gift(giftId, recipient, targetLocalRefId, envelope)
op:withdraw-gift(giftId, gifter, withdrawPromiseRefId, envelope)
op:flush(refId)                  -- OpFlushProtocol only
op:flush-ack(refId)              -- OpFlushProtocol only
op:e-flush-probe(originPeer, originRefId, refId)
                                 -- EJavaFlush slow path, also
                                    OpFlushProtocol resolver->target
op:e-flush-probe-ack(originRefId)
                                 -- ack for op:e-flush-probe
```

**Descriptors** (values that appear in field slots of messages; never on
the wire by themselves):

```
desc:handoff-give(gifter, targetHost, giftId, envelope)
desc:remote-target(peer, refId)
```

`op:resolve`'s `value` slot is a tagged union over `desc:remote-target`
and `desc:handoff-give`. A `desc:remote-promise` variant would be
required to land distributed inter-vat promise shortening — see
[`path-changes.md`](path-changes.md) §1.2.b. The target host's
response to an `op:withdraw-gift` is just an
`op:resolve(withdrawPromiseRefId, desc:remote-target(...))` — same
`op:resolve` message, different `value` variant. No separate "gift
response" message exists.

`op:resolve` identifies the resolver side via the channel's `from` field;
the `targetRefId` identifies the specific `RemotePromise` *on the listener*
that is being resolved. This is the OCapN "answer position" / "import-table
key" mapped into our model.

## 6. Gift-table semantics

Each peer that hosts gifts maintains a gift table keyed by `(gifter,
giftId)`:

Gifts and the gifter-side counter are fields of the per-peer `vats[p]`
record (`vats[p].gifts` and `vats[p].nextGiftId`); see `lib/PeerState.tla`.

```tla
vats[p].gifts : [Peers -> [GiftIds -> GiftEntry \cup {NoGift}]]

GiftEntry == [kind : {"gift"}, recipient : Peers, targetLocalRefId : Nat]
```

- `vats[targetHost].gifts[gifter][giftId]` is the deposited gift on
  `targetHost`, deposited by `gifter`, awaiting withdrawal by
  `recipient`.
- `giftId` is **gifter-scoped**: each gifter allocates a fresh giftId
  from its own counter `vats[gifter].nextGiftId` on every deposit.
  `(alice, 1)` and `(bob, 1)` are distinct gift entries.
- Multiple in-flight handoffs at the same `targetHost`, originated by
  different gifters, coexist without collision.
- A gifter never re-uses a `(gifter, giftId)` pair until the gift has
  been withdrawn (or expired): `vats[gifter].nextGiftId` is monotone
  and only the gifter writes it.
- Envelope authentication is out of scope for the v0 model.

**Bounding for TLC.** `GiftIds == 1..MaxGifts` for a per-MC `MaxGifts`
constant. `vats[p].nextGiftId \in 0..(MaxGifts + 1)` is part of
`VatStateType`; an MC that would exhaust giftIds disables further
`HandoffInitiate` rather than wrapping.

### Gift lifecycle (one-shot)

```
Empty --[op:deposit-gift received]--> Pending
Pending --[op:withdraw-gift received, envelope matches recipient]--> Empty
```

A gift entry is created when the target host processes `op:deposit-gift`
from the gifter, and is **removed atomically** in the same step that
processes the matching `op:withdraw-gift`. No other action ever mutates a
`vats[*].gifts[*][*]` slot.

Captured as invariants:

- **`GiftOneShot`** — once redeemed, never seen again. Any subsequent
  `op:withdraw-gift(giftId, gifter, ...)` arriving at the target host
  finds `LocalGift(self, gifter, giftId) = NoGift` and is rejected
  (modelled as a no-op + trace marker; never silently re-deposit). The
  `vats[gifter].nextGiftId` monotonicity guarantees a re-allocated
  giftId never collides with an old one.
- **`GiftHasOneRecipient`** — for as long as
  `vats[targetHost].gifts[gifter][giftId] # NoGift`, only the recipient
  named in the entry's `recipient` field can successfully withdraw it.
  The `op:withdraw-gift` handler verifies `recipient = msg.from`; any
  other peer's withdraw is silently dropped.

## 7. 3PHO walkthrough (resolver-driven)

Concrete chain example for `host[N-1]` resolving `p_{N-1}` to
`T@host[N]`, with listener `host[N-2]`. The resolver is also the
gifter; the listener is the recipient; `host[N]` is the target host.

Pre-state:

- `vats[host[N-1]].refs[p_{N-1}]` is a `LocalPromise` with listener
  `host[N-2]`, queue possibly non-empty (pre-resolve pipelined messages).
- `vats[host[N-1]].refs[r_T] = RemoteTarget(host[N], r_T_local)`.
- `vats[host[N-2]].refs[p_{N-1}] = RemotePromise(host[N-1], p_{N-1},
  localResolution=<none>)` — and was used to pipeline some
  `op:deliver-only`s sent at `host[N-2]` toward `host[N-1]`.
- `vats[host[N]].refs[r_T_local] = LocalTarget(sink)`.
- `vats[host[N]].gifts` empty; `vats[host[N-1]].nextGiftId = 1`.

Step-by-step:

1. **Gifter fires** `HandoffInitiate` (in this spec, handoff is
   initiated independently of `ResolverResolve`; the resolver-driven
   variant in the OCapN proposal is equivalent). Atomically:
   - allocate `giftId = vats[gifter].nextGiftId`; increment counter.
   - allocate `pw = nextRefId`; increment counter.
   - append `op:deposit-gift(giftId, recipient=host[N-2],
     targetLocalRefId=r_T_local, pw)` to
     `channels[host[N-1]][host[N]]`.
   - append `op:resolve(targetRefId=pw,
     value=desc:handoff-give(gifter=host[N-1], targetHost=host[N],
     giftId, pw))` to `channels[host[N-1]][host[N-2]]`.
   - (Chain-form variant: `targetRefId` is an existing forwarder
     `RemotePromise` on the gifter, not `pw`.)
2. **`host[N]` receives** `op:deposit-gift`. Atomically installs
   `vats[host[N]].gifts[host[N-1]][giftId] = {recipient: host[N-2],
   targetLocalRefId: r_T_local}` and pre-mints
   `vats[host[N]].refs[pw] = LocalPromise(queue=<empty>,
   listeners={host[N-2]}, resolution=<none>)` so that pipelined sends
   on the recipient's `RemotePromise(pw)` have somewhere to queue
   before the withdraw arrives.
3. **`host[N-2]` receives** `op:resolve(pw, desc:handoff-give(...))` via
   `ReceiveNetwork`. Atomically:
   - install `vats[host[N-2]].refs[pw] = RemotePromise(host[N], pw,
     localResolution=<none>)`. `host[N-2]` cannot dispatch on the
     `resolverRefId` for anything other than "send to `host[N]`".
   - append `op:withdraw-gift(giftId, gifter=host[N-1],
     withdrawPromiseRefId=pw)` to `channels[host[N-2]][host[N]]`.
   - (Chain-form: also set
     `vats[host[N-2]].refs[targetRefId].localResolution = ResRef(pw)`
     so future sends on the existing forwarder hop through `pw`.)
4. **`host[N]` receives** `op:withdraw-gift`. **All atomic, to preserve
   `PairingInvariant`:**
   - look up `vats[host[N]].gifts[host[N-1]][giftId]`.
   - **disable** if the slot is empty (deposit not yet processed; the
     message stays at the head of the inbox until the deposit lands).
   - **silently drop** if `recipient # msg.from` (`GiftHasOneRecipient`
     enforcement).
   - otherwise: install
     `vats[host[N]].refs[pw].resolution = ResRef(host[N], r_T_local)`
     and `vats[host[N]].refs[pw].notified = TRUE`; append a direct
     `op:resolve(pw, desc:remote-target(host[N], r_T_local))` to
     `channels[host[N]][host[N-2]]`. *No nested 3PHO*.
   - clear `vats[host[N]].gifts[host[N-1]][giftId] := NoGift` (one-shot
     consumption) in the same `vats EXCEPT` update.
5. **`host[N-2]` receives** `op:resolve(pw, desc:remote-target(host[N],
   r_T_local))` via `ReceiveNetwork`. Installs
   `vats[host[N-2]].refs[pw].localResolution = RemoteTarget(host[N],
   r_T_local)`.

### Pipelined-pre-resolve sends

Between steps 1 and 4, `host[N-2]` can pipeline sends on `pw` →
routed over `channels[host[N-2]][host[N]]`. The `op:deliver-only`
carries `pw` as its refId; `host[N]` looks up `LocalRef(host[N], pw)`.
*Before* step 2, that lookup is `EntryNone` — the message is held at
the head of the inbox pending receipt of `op:deposit-gift`. *After*
step 2 but before step 4, the message lands in
`vats[host[N]].refs[pw].queue` as ordinary `LocalPromise` queue
traffic; step 4's resolve-to-`r_T_local` then drains the queue via
the intra-vat cascade.

This matches OCapN reality: pipelined messages on a handed-off ref
*can* reach the target before the recipient has learned the target's
identity, and they're held at the target host as ordinary queued
messages on the target host's local presence for the withdraw-promise.

### Deposit/withdraw FIFO ordering

The deposit (`op:deposit-gift`) is sent on
`channels[host[N-1]][host[N]]`. The recipient's eventual
`op:withdraw-gift` lands on `channels[host[N-2]][host[N]]`. These are
*different* wires, so per-pair FIFO does **not** guarantee the deposit
arrives before the withdraw. The spec explicitly orders them via the
`op:withdraw-gift` branch of `ReceiveNetwork`: it is disabled until
`LocalGift(self, gifter, giftId) # NoGift`, naturally serializing on
the deposit.

## 8. Subscribe-to-already-resolved

When `op:listen(subscriber, refId)` arrives at `h` and
`vats[h].refs[refId].resolution # ResNone`:

- Immediately reply with the same `op:resolve(refId, value)` the
  resolver would have sent when it first resolved:
  - `value = desc:remote-target(...)` if the resolution is a
    `LocalTarget` on `h` (bypass case).
  - Fresh 3PHO triplet (`op:deposit-gift` to target host plus
    `op:resolve(..., desc:handoff-give(...))` to `subscriber`,
    consuming a fresh `vats[h].nextGiftId`) if the resolution is a
    `RemoteTarget`. *Not modelled in v0; see
    [`notes/path-changes.md`](path-changes.md).*

The handler also records `subscriber` in `vats[h].refs[refId].listeners`
for bookkeeping. If `vats[h].refs[refId].resolution = ResNone`, the
handler just records the listener for future notification by
`ResolverResolve`.

## 9. `op:flush` — resolver-initiated, pushes upstream (locality-clean)

Triggered when a `LocalPromise pa` at resolver `H` is about to fire
`op:resolve(targetRefId, R')` for some `R' \in Target`. The mechanism
below is exactly what `spec/PromiseResolution.tla`'s `OpFlushProtocol`
policy implements; it is locality-clean (every read is the actor's own
state or an incoming message, every state transition is driven by an
explicit protocol message).

1. `H` enumerates listeners `pa.listeners`.
2. For each `L_i`, `H` appends `op:flush(refId)` to `channels[H][L_i]`
   and stores `pa.flushPending = pa.listeners`.
3. `L_i` receives `op:flush(refId)`. In a single atomic step it sets
   `embargo = TRUE` on its `RemotePromise(H, refId)` **and** enqueues
   `op:flush-ack(refId)` on `channels[L_i][H]`. Because that channel is
   p2p FIFO, the ack queues behind any of `L_i`'s previously-pipelined
   `op:deliver-only` sends for this ref — `H` is guaranteed to have
   dequeued (and forwarded onward) every one of them before it dequeues
   the ack. No "wait for my outbox to drain" step is needed; FIFO does
   the work.
4. `H` receives `op:flush-ack(refId)` from each `L_i` and removes the
   listener from `pa.flushPending`. New `op:deliver-only` sends from
   any `L_i` to `H` cannot arrive after the corresponding ack (FIFO),
   so once `pa.flushPending = {}` no further pre-flush sends from
   listeners can race into `pa.queue`.
5. `H` drains `pa.queue` through its own kind-dispatch (which may
   include intra-vat cascade into the resolution).
6. `H` emits **`op:e-flush-probe(originPeer=H, originRefId=pa, refId=R')`**
   on `channels[H][R'.targetPeer]` (action `SendTargetFlushProbe`).
   The probe rides that channel BEHIND any of `H`'s previously-
   forwarded `op:deliver-only` sends for this ref. `pa.flushPhase`
   transitions `"idle" -> "out"`.
7. `R'.targetPeer` receives the probe at its `LocalTarget` terminus
   and emits `op:e-flush-probe-ack(originRefId=pa)` directly back on
   `channels[R'.targetPeer][H]`.
8. `H` receives `op:e-flush-probe-ack`; `pa.flushPhase` transitions
   `"out" -> "acked"`. This is the only signal `H` consumes to know
   its forwards have been processed at the target — it is an explicit
   protocol-level ack, not an outbox-empty inference.
9. `H` fires `SendOpResolveAfterFlush`: for each `L_i`, allocates a
   fresh `giftId`, deposits the gift at `R'.targetPeer`
   (`op:deposit-gift`), and appends
   `op:resolve(L_i's-refId-for-pa, desc:handoff-give(...))` to
   `channels[H][L_i]`. From here the 3PHO withdraw round-trip
   (steps 3-5 of §7) plays out.

The point: by step 4, no pre-flush `op:deliver-only` traffic from any
listener for `pa` can still be in flight on any wire to `H` (FIFO
gives that for free); by step 8, no pre-flush forward from `H` to the
target can still be in flight on `channels[H][R'.targetPeer]` (the
probe-ack gives that explicitly). When each `L_i` switches to the new
route at step 9 nothing can race it via the old route, and no peer
ever inspected another peer's channel state to reach that conclusion.

## 10. `EJavaFlush` — subscriber-initiated, faithful DelayedRedirector model

### 10.1 What e-on-java actually does (DelayedRedirector)

The policy this spec calls `EJavaFlush` is a faithful model of the
e-on-java `DelayedRedirector` protocol. This subsection walks through
the real protocol first, §10.2 documents what the spec implements,
and §10.3 explains why any *local-only* embargo signal (such as
"my outbox is empty") would be strictly weaker.

In [e-on-java](https://github.com/kpreid/e-on-java) every `RemotePromise`
carries an `isFresh` bit
([`RemotePromiseHandler.java`](https://github.com/kpreid/e-on-java/blob/a0b3b599cf267b3138eea5f5fb83f27cebd28373/src/jsrc/net/captp/jcomm/RemotePromiseHandler.java#L40-L66)),
flipped to `false` the first time anything is pipelined on it. When the
promise's redirection arrives at the subscriber, dispatch goes through
[`DelayedRedirector.run`](https://github.com/kpreid/e-on-java/blob/a0b3b599cf267b3138eea5f5fb83f27cebd28373/src/jsrc/org/erights/e/elib/ref/DelayedRedirector.java#L50-L107):

- **Fast path — no flush needed.** If `isFresh()`,
  `sameConnection(target)`, or `isDeepFrozen(target)` is true
  ([L63](https://github.com/kpreid/e-on-java/blob/a0b3b599cf267b3138eea5f5fb83f27cebd28373/src/jsrc/org/erights/e/elib/ref/DelayedRedirector.java#L63)),
  resolve to the new target immediately. `sameConnection` covers the
  two-party case (new target lives in the same vat as the current
  resolver), where p2p FIFO over the single wire already orders things.

- **Slow path — downstream flush + ack.** Otherwise
  ([L88-L108](https://github.com/kpreid/e-on-java/blob/a0b3b599cf267b3138eea5f5fb83f27cebd28373/src/jsrc/org/erights/e/elib/ref/DelayedRedirector.java#L88)),
  mint a fresh local promise+resolver `(p_new, r_new)`, wrap `r_new` in
  a `Redirector`, and then:

      E.sendOnly(myOptProxy, "__whenMoreResolved", rdr);
      myOptResolver.resolve(pair[0]);   // resolve to p_new

  This sends a **second** `__whenMoreResolved` message on the ORIGINAL
  proxy (i.e. on the wire to the current resolver). The sentinel rides
  the same channel as previously-pipelined sends and is re-forwarded by
  every hop just like a regular message; it eventually arrives at the
  actual target. The target's reply (a `run(real_target)` to the
  redirector) is the ack that travels all the way back to the
  subscriber. Until that ack returns, new sends queue locally in
  `p_new`; when it returns, `p_new` resolves and the buffered messages
  drain.

The crucial property: the sentinel and ack do an **end-to-end roundtrip
through the entire chain** before the subscriber commits to the new
path. By construction, every previously-pipelined send must have been
processed at the eventual target before the ack returns.

### 10.2 What the `EJavaFlush` policy in this spec actually does

`spec/PromiseResolution.tla`'s `"EJavaFlush"` is a faithful model of
DelayedRedirector. It tracks the per-`RemotePromise` `fresh` sticky bit,
implements the fast-path predicates locally, and emits an end-to-end
flush sentinel + ack on the slow path.

State additions:

- `vats[L].refs[r].fresh` — Boolean, set `TRUE` at `RemotePromise`
  construction, cleared `FALSE` by `ApplyRoute` (via `MarkRefNonFresh`)
  the first time `L` takes a `"wire"` route originating at this ref.
  Once cleared, it stays cleared.

Wire messages:

- `op:e-flush-probe(originPeer, originRefId, refId)` — downstream
  flush sentinel. Routed by `Route` exactly like `op:deliver-only`
  (queues at unresolved `LocalPromise`s, holds at embargoed
  `RemotePromise`s, forwards through `RemoteTarget`s, etc.). Carries
  the originator's identity and ref as a return address. The same
  wire message is used by EJavaFlush (originator is a subscriber
  holding a `RemotePromise`) and OpFlushProtocol (originator is a
  resolver holding a `LocalPromise`); only the ack-receive dispatch
  differs.
- `op:e-flush-probe-ack(originRefId)` — direct ack to the
  `originPeer`. Carries only the `originRefId` so the originator can
  match it to its outstanding state.

Receive of `op:resolve(r, desc:remote-target(p, r'))` at `L`:

1. Evaluate **fast-path** predicates (purely local at `L`, via
   `LocalRef(L, r)`):
   - `isFresh := LocalRef(L, r).fresh`
   - `sameConn := msg.value.peer = LocalRef(L, r).resolverPeer`
   - `fastPath := isFresh \/ sameConn`
2. If `fastPath`: install `localResolution = ResRef(p, r')`; `embargo`
   stays `FALSE`. Future sends route directly through the installed
   `localResolution` via the normal `Route` recursion.
3. Otherwise (**slow path**): stage `localResolution = ResRef(p, r')`,
   set `embargo = TRUE`, and append
   `OpEFlushProbe(L, r, LocalRef(L, r).resolverRefId)` to
   `channels[L][LocalRef(L, r).resolverPeer]` (via
   `AppendToOutbox(_, L, LocalRef(L, r).resolverPeer, _)`). The probe
   rides the same wire as previously-pipelined sends.
4. While `embargo` is set, `Route(L, r)` returns `"hold"`; new sends
   buffer in `vats[L].refs[r].pending`.

Receive of `op:e-flush-probe`:

- At an intermediate hop with a `RemotePromise`/`RemoteTarget`/resolved
  `LocalPromise`: re-forward via `Route` + `ApplyRoute` (same dispatch
  as `op:deliver-only`).
- At a `LocalTarget` host `X` (terminal): `ApplyRoute`'s `"deliver"`
  branch is polymorphic on `msg.op` and emits
  `OpEFlushProbeAck(originRefId)` on `channels[X][originPeer]`
  instead of appending to `delivered`.

Receive of `op:e-flush-probe-ack` (polymorphic on the originator's
entry kind at `LocalRef(self, originRefId)`):

- **EJavaFlush** (originator is a subscriber holding a
  `RemotePromise`): assert `embargo = TRUE`, set `embargo = FALSE`.
  `ProcessHold` can then drain `vats[self].refs[originRefId].pending`
  to the newly-committed post-resolution path.
- **OpFlushProtocol** (originator is a resolver holding a
  `LocalPromise`): assert `flushPhase = "out"`, set
  `flushPhase = "acked"`. `SendOpResolveAfterFlush` is now enabled
  and will emit `op:resolve` to listeners.

Locality contract: every read above is the actor's own state or the
contents of an incoming message. The only triggers that clear the
embargo (EJavaFlush) or advance the flush phase (OpFlushProtocol) are
protocol messages (the probe-ack). No action infers "the recipient has
processed" from "my outbox is empty" — channel state is not used as a
signal in either policy.

### 10.3 Why a local "outbox empty" signal is insufficient (3-chain witness)

Any implementation that lifts the slow-path embargo by inspecting `L`'s
own outbox to the resolver — waiting for `channels[L][resolverPeer]` to
drain of `op:deliver-only` for the matching `refId` — is a strictly
weaker check than the faithful e-on-java protocol. The check is local
(`L` reads only its own outbox), but it conflates "left my outbox" with
"reached the eventual target", and fails for chains ≥ 3 hops:

```
Topology: vatA → vatB(p1) → vatC(p2) → vatD(T)
[s7]  vatB forwards seq=1 onto channels[vatB][vatC]
[s8]  vatC drains and forwards onto channels[vatC][vatD]
[s9]  vatB receives op:resolve(r=2, vatD/3) from vatC.
      An outbox-empty check on channels[vatB][vatC] -- now empty --
      returns FALSE.  installNow fires with no embargo.
[s10] vatB receives seq=2 from vatA; Route routes via
      localResolution=vatD/3; sends on channels[vatB][vatD],
      bypassing vatC entirely.
[s11] vatD receives seq=2.  <-- delivered first
[s12] vatD receives seq=1.  <-- delivered second
      EndToEndRefFIFO violated: delivered order [2, 1].
```

The faithful EJavaFlush implemented in this spec handles this case as
follows: at s9 the `fresh` bit on `vats[vatB].refs[2]` is `FALSE`
(cleared at s7 when vatB forwarded seq=1) and `sameConnection` is
`FALSE` (vatD ≠ vatC), so the slow path fires. vatB emits an
`op:e-flush-probe` on `channels[vatB][vatC]` and sets `embargo = TRUE`.
The probe re-forwards through vatC to vatD, where it queues behind the
in-flight seq=1. When vatD receives the probe, it emits
`op:e-flush-probe-ack` directly back to vatB on
`channels[vatD][vatB]`. By the time the ack reaches vatB, seq=1 has
been delivered at vatD. vatB lifts the embargo, drains
`vats[vatB].refs[2].pending`, and seq=2 follows in order.

`MC_EJavaFlush_3Chain` passes with the current design.

### 10.4 Tribble 4-way caveat

A faithful implementation of the e-on-java protocol is known to be
defeated by the four-party scenario where intermediate hops are
themselves concurrently undergoing a path change while the sentinel
traverses the chain. The end-to-end sentinel preserves ordering for a
single linear chain but can race against parallel path changes on the
path it traverses. The Ridley `op:flush` proposal addresses this by
inverting the direction of the flush; the `OpFlushProtocol` policy in
this spec is a faithful model of that design's three-party form, with
the same probe + ack primitive used by EJavaFlush layered underneath
to keep the resolver-to-target flush locality-clean (§11). The
four-party form (and the inter-vat distributed promise-shortening
machinery required to even model the four-way race in TLC) is tracked
in [`path-changes.md`](path-changes.md) §3.1. See the
[ocapn#11 thread](https://github.com/ocapn/ocapn/issues/11) for the
running OCapN discussion.

## 11. Worked example trace (4-chain, both flush protocols)

Chain: `HeadPeer → p_1@host[1] → p_2@host[2] → p_3@host[3] → T@host[4]`.

Under terminal-only propagation only one `op:resolve` ever fires — the
one from `host[3]` to `host[2]` carrying `T@host[4]`. Only `host[2]`
undergoes a wire-visible path change. The race is between:

- **Old path** `host[2] → host[3] → host[4]`: pre-resolve
  `op:deliver-only`s from `host[2]` (forwarded from upstream) sitting on
  `channels[host[2]][host[3]]`, eventually reaching `host[4]` via
  `channels[host[3]][host[4]]`.
- **New path** `host[2] → host[4]`: post-resolve sends from `host[2]`
  routing via the installed `localResolution` directly to `host[4]` on
  `channels[host[2]][host[4]]`.

**`OpFlushProtocol` (resolver-initiated, locality-clean):** `host[3]`
sends `op:flush(p_2)` to `host[2]`. `host[2]` atomically sets
`embargo = TRUE` on its `RemotePromise(host[3], 2)` *and* enqueues
`op:flush-ack(2)` on `channels[host[2]][host[3]]`. Because that channel
is p2p FIFO, the ack queues behind any of `host[2]`'s previously-
pipelined ref-1 sends — `host[3]` is guaranteed to have processed (and
forwarded onward) every one of them before dequeuing the ack. No
"outbox drained" inference is needed; FIFO does the work
(§10.5).

Once all listener acks are in and `host[3]`'s own `LocalPromise.queue`
is drained, `host[3]` fires `SendTargetFlushProbe`: emits
`op:e-flush-probe(host[3], p_2, T's refId)` on
`channels[host[3]][host[4]]`. The probe rides that channel BEHIND any
of `host[3]`'s previously-forwarded ref-1 sends. `host[4]` receives
the probe at its `LocalTarget` terminus and emits
`op:e-flush-probe-ack` directly back on `channels[host[4]][host[3]]`.
On ack receipt at `host[3]`, the resolver's `LocalPromise.flushPhase`
  transitions `"out" -> "acked"`, which enables
`SendOpResolveAfterFlush`: `host[3]` emits `op:resolve(p_2,
desc:remote-target(host[4], T's refId))` to `host[2]`. `host[2]`'s
subsequent sends on the post-resolution path strictly follow all
old-path traffic.  **FIFO preserved.**

Critically, every state transition in this protocol is driven by an
explicit protocol message (`op:flush`, `op:flush-ack`,
`op:e-flush-probe`, `op:e-flush-probe-ack`) and every precondition
reads only the actor's own `LocalRef(self, r)` state. No action
observes the other end of any channel, and no action treats "my outbox
is empty" as "the recipient has processed". The probe + ack mechanism is
exactly the same primitive used by EJavaFlush's slow path; only the
originator's entry kind (`RemotePromise` for EJavaFlush vs
`LocalPromise` for OpFlushProtocol) differs in the ack-receive
dispatch.

**`EJavaFlush` (this spec's faithful DelayedRedirector model):**
`host[3]` immediately deposits the gift and fires `op:resolve(p_2,
desc:handoff-give(...))` to `host[2]`. `host[2]`'s `fresh` bit on the
relevant `RemotePromise` is `FALSE` (it has already pipelined sends
through) and `sameConnection` is `FALSE` (the new target host[4] is in a
different vat than the current resolver host[3]). Slow path fires:
`host[2]` sets `embargo = TRUE`, stages the `localResolution`, and emits
`op:e-flush-probe` on `channels[host[2]][host[3]]`. The probe rides the
same wire as previously-pipelined sends and gets re-forwarded by
`host[3]` to `host[4]`, queueing behind any in-flight ref-1 backlog. When
`host[4]` receives the probe it emits `op:e-flush-probe-ack` directly
back to `host[2]` on `channels[host[4]][host[2]]`. On ack receipt,
`host[2]` lifts the embargo; `ProcessHold` drains the locally-buffered
pending sends to the now-committed post-resolution path. **FIFO
preserved** for the 3-chain case. The Tribble four-way case (§10.4)
remains a known limitation of the underlying protocol.

For tracked future work (Tribble four-way, distributed inter-vat
promise shortening, ref-scoped drainage, per-peer refId namespaces,
multi-sender FIFO, flush-under-handoff) see
[`path-changes.md`](path-changes.md) §3.
