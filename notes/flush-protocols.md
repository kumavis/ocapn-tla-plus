# Flush protocols, local shortening, terminal-only propagation, and 3PHO

This note is the **specification reference** for the upcoming refactor of
[`spec/PromiseResolution.tla`](../spec/PromiseResolution.tla) toward an
OCapN-flavored reference model. It precedes any code changes; the TLA edits
must implement what is written here.

## Vocabulary

- **shorten** (verb) — install a new route through a ref so subsequent
  sends bypass an old hop. Never *shortcut*.
- **local shortening** — a `LocalPromise` at peer `H` resolves to another
  ref *also hosted at* `H`; `H` drains the resolving promise's queue
  directly into the new ref. **No wire traffic** generated by the shortening
  itself.
- **distributed shortening** — a holder of a `RemotePromise` installs a
  `localResolution` and starts dispatching through it. Enabled by Phase 1c's
  per-`RemotePromise.localResolution` slot; **out of scope** for this
  iteration (we install the substrate but never propagate further
  upstream).
- **terminal-only resolution propagation** — `op:resolve(targetRefId, value)`
  is sent to a listener *only* when `value` denotes a `Target` (`LocalTarget`
  or `RemoteTarget`). When the resolution is a `Promise`, listeners stay on
  their `RemotePromise` route; the resolver keeps forwarding through its
  own queue / local-shortening machinery.
- **`op:resolve`** — wire message previously named `op:resolve-notify`.
  Renamed in Phase 1a.

## 1. Reference taxonomy

```
Reference        = Promise | Target
Promise          = LocalPromise | RemotePromise
Target           = LocalTarget | RemoteTarget
RemoteReference  = RemotePromise | RemoteTarget
LocalReference   = LocalPromise | LocalTarget
```

Each peer maintains a partial map `refs[p][refId] = entry`. The entry's
`kind` field discriminates the four cases:

| `kind`          | Fields                                                                |
| --------------- | --------------------------------------------------------------------- |
| `LocalTarget`   | `sink` — the message sink (delivered log in our model)                |
| `RemoteTarget`  | `targetPeer`, `targetRefId`                                           |
| `LocalPromise`  | `queue`, `listeners`, `resolution` (`<none>` or a `Reference`)        |
| `RemotePromise` | `resolverPeer`, `resolverRefId`, `localResolution` (`<none>` or ref)  |

### Pairing invariant — every remote ref has a local presence

Every `RemoteX` on peer A is the local-side presence of a corresponding
`LocalX` on the peer whose name it carries. Quantified over the *allocated*
domain `DOM(refs[p])` only:

```tla
PairingInvariant ==
    /\ \A p \in Peers, r \in DOM(refs[p]) :
         refs[p][r].kind = "RemoteTarget" =>
            LET q == refs[p][r].targetPeer
                rq == refs[p][r].targetRefId
            IN rq \in DOM(refs[q]) /\ refs[q][rq].kind = "LocalTarget"
    /\ \A p \in Peers, r \in DOM(refs[p]) :
         refs[p][r].kind = "RemotePromise" =>
            LET q == refs[p][r].resolverPeer
                rq == refs[p][r].resolverRefId
            IN rq \in DOM(refs[q]) /\ refs[q][rq].kind = "LocalPromise"
```

A single `Local*` entry on peer `q` may be the presence of many `Remote*`
entries across other peers — that's the natural many-to-one shape of a
capability with many holders. The invariant *must* be preserved by every
action that mints a new ref entry (chain `Init`, the 3PHO actions in
Phase 3).

### refId namespacing (v0 convention)

For this iteration the model uses **globally-unique refIds shared across
peers**: a single integer `r` identifies the same logical capability
everywhere it appears. Both the resolver-side `LocalPromise` and a
holder's `RemotePromise` use the same `r`; both the target host's
`LocalTarget` and any holder's `RemoteTarget` use the same `r`. This
keeps `op:resolve(targetRefId, value)` trivially well-defined and matches
the existing chain models' shared `PromiseRefs` convention.

Real OCapN uses per-peer (per-session) refId namespaces: each peer
maintains its own import/export tables, and messages reference refIds in
the destination peer's namespace. `op:listen(subscriberRefId,
resolverRefId)` would carry both sides' refIds so the resolver knows
which answer-position to address its `op:resolve` to. Translating the v0
model to per-peer namespaces is a mechanical change and is out of scope
here.

### `LocalPromise.resolution` vs `RemotePromise.localResolution`

These are deliberately different fields and the names should not be
conflated:

- `LocalPromise.resolution` — the promise's **actual resolution**, set by
  `ResolverResolve` at the resolver peer. Once non-`<none>`, the promise
  *is* that ref. Drives local shortening at the resolver and listener
  notification.
- `RemotePromise.localResolution` — what the *holder* has **learned
  about** the promise's resolution, via `op:resolve`. Once non-`<none>`,
  the holder can shorten its own dispatch through the new ref (subject to
  flush-protocol gating). The remote `LocalPromise.resolution` may have
  been set well before any holder's `localResolution` catches up.

## 2. Sending semantics (single dispatch)

When peer `self` is asked to send `m` via refId `r`:

| `refs[self][r].kind`                | Action                                          |
| ----------------------------------- | ----------------------------------------------- |
| `LocalTarget`                       | apply `m` to `entry.sink` (deliver)             |
| `RemoteTarget`                      | append `op:deliver-only(...)` to `channels[self][entry.targetPeer]` |
| `LocalPromise` (unresolved)         | append `m` to `entry.queue`                     |
| `LocalPromise` (resolved)           | recurse on `entry.resolution` (send-time local shortening) |
| `RemotePromise` (no localResolution)| append `op:deliver-only` to `channels[self][entry.resolverPeer]` |
| `RemotePromise` (with localResolution) | recurse on `entry.localResolution`           |

## 3. Local shortening (intra-vat queue handoff)

When a `LocalPromise pa` at peer `H` becomes resolved to `R'`, and
`R'` is hosted at the *same* `H`:

- If `R'.kind = LocalTarget`: each `m \in pa.queue` is applied to
  `R'.sink` (delivered).
- If `R'.kind = LocalPromise pb`: prepend / append `pa.queue` into
  `pb.queue`. (`pb` may itself be resolved → recurse: the **queue-handoff
  cascade** runs entirely inside `H`.)

No wire traffic generated by the shortening. This is the *only*
promise-to-promise shortening we model in this iteration.

If `R'` is a remote ref (`RemoteTarget` / `RemotePromise`), the queue is
drained over the wire to `R'`'s peer (same as today's `ProcessPending`).

## 4. Terminal-only resolution propagation

When a `LocalPromise pa` at `H` becomes resolved to `R'`:

| `R'.kind`              | Notify listeners?                              | 3PHO? |
| ---------------------- | ---------------------------------------------- | ----- |
| `LocalTarget`          | Yes — `op:resolve(targetRefId, desc:remote-target(H, R'_local))` per listener | No — listener already has session with `H` |
| `RemoteTarget`         | Yes — `op:resolve(targetRefId, desc:handoff-give(...))` per listener | **Yes** — listener has no session with `R'.targetPeer` |
| `LocalPromise`         | **No** — silent; listeners stay on their `RemotePromise` to `H`; `H` drains `pa.queue` into `R'.queue` (local shortening) | n/a |
| `RemotePromise`        | **No** — silent; listeners stay on their `RemotePromise` to `H`; `H` drains `pa.queue` over the wire to `R'.resolverPeer` | n/a |

Listeners that receive `op:resolve` do **not** further propagate. They
never `op:listen` on the new ref, never send `op:resolve` to their own
listeners. That's the next-iteration "distributed P2P shortening" we're
deferring.

Rule of thumb: an `op:resolve` is sent iff the resolution introduces the
listener to a *terminal* capability (`Target`). When `R'` is a peer the
listener already knows (`LocalTarget` on `H`), the bypass uses a plain
`desc:remote-target`; when `R'` is a third peer, 3PHO is required.

## 5. Wire messages and descriptors

**Messages** (travel on `channels[from][to]` and consume FIFO slots):

```
op:deliver-only(sender, sentOnRef, seq, pos)
op:resolve(targetRefId, value)
op:listen(subscriber, refId)
op:deposit-gift(giftId, recipient, targetLocalRefId, envelope)
op:withdraw-gift(giftId, gifter, withdrawPromiseRefId, envelope)
op:flush(refId)                  -- op:flush protocol only
op:flush-ack(refId)              -- op:flush protocol only
```

**Descriptors** (values that appear in field slots of messages; never on
the wire by themselves):

```
desc:handoff-give(gifter, targetHost, giftId, envelope)
desc:remote-target(peer, refId)
```

`op:resolve`'s `value` slot is a tagged union over `desc:remote-target`
and `desc:handoff-give` (and may grow other variants like
`desc:remote-promise` once distributed P2P shortening lands). The target
host's response to an `op:withdraw-gift` is just an
`op:resolve(withdrawPromiseRefId, desc:remote-target(...))` — same
`op:resolve` message, different `value` variant. No separate "gift
response" message exists.

`op:resolve` identifies the resolver side via the channel's `from` field;
the `targetRefId` identifies the specific `RemotePromise` *on the listener*
that is being resolved. This is the OCapN "answer position" / "import-table
key" mapped into our model.

## 6. Gift-table semantics

Each peer that hosts gifts maintains a gift table keyed by `(gifter,
giftId)`:

```tla
gifts : [Peers -> [Peers \X GiftIds -> GiftEntry \cup {<<>>}]]

GiftEntry == [recipient : Peers, targetLocalRefId : RefIds, envelope : Envelopes]
```

- `gifts[targetHost][gifter, giftId]` is the deposited gift on
  `targetHost`, deposited by `gifter`, awaiting withdrawal by
  `recipient`.
- `giftId` is **gifter-scoped**: gifter allocates a fresh giftId from its
  own counter / namespace per deposit. `(alice, 1)` and `(bob, 1)` are
  distinct gift entries.
- Multiple in-flight handoffs at the same `targetHost`, originated by
  different gifters, coexist without collision.
- A gifter never re-uses a `(gifter, giftId)` pair until the gift has
  been withdrawn (or expired). Modeled by a per-peer monotonic counter
  `nextGiftId[gifter]` allocated at `op:deposit-gift` time.
- The `envelope` is an opaque token bound to `(gifter, giftId, recipient,
  targetHost)` — modelled as a single opaque value; real OCapN uses a
  signed assertion.

**Bounding for TLC.** `GiftIds == 0..MaxGifts` for a per-MC `MaxGifts`
constant. A guarding state invariant `\A p \in Peers : nextGiftId[p] \in
0..MaxGifts` prevents counter overflow; an MC that exhausts giftIds is
reported as a model-size error rather than wrapping.

### Gift lifecycle (one-shot)

```
Empty --[op:deposit-gift received]--> Pending
Pending --[op:withdraw-gift received, envelope matches recipient]--> Empty
```

A gift entry is created when the target host processes `op:deposit-gift`
from the gifter, and is **removed atomically** in the same step that
processes the matching `op:withdraw-gift`. No other action ever mutates a
`gifts[*][*]` slot.

Captured as invariants:

- **`GiftOneShot`** — once redeemed, never seen again. Any subsequent
  `op:withdraw-gift(giftId, gifter, ...)` arriving at the target host
  finds `gifts[self][gifter, giftId] = <<>>` and is rejected (modelled as
  a no-op + trace marker; never silently re-deposit). The
  `nextGiftId[gifter]` monotonicity guarantees a re-allocated giftId
  never collides with an old one.
- **`GiftHasOneRecipient`** — for as long as `gifts[targetHost][gifter,
  giftId] /= <<>>`, only the recipient named in the entry's `recipient`
  field can successfully withdraw it. The `op:withdraw-gift` handler
  verifies `recipient = msg.from`; any other peer's withdraw is rejected.

## 7. 3PHO walkthrough (resolver-driven)

Concrete chain example for `host[N-1]` resolving `p_{N-1}` to
`T@host[N]`, with listener `host[N-2]`. The resolver is also the
gifter; the listener is the recipient; `host[N]` is the target host.

Pre-state:

- `refs[host[N-1]][p_{N-1}]` is a `LocalPromise` with listener
  `host[N-2]`, queue possibly non-empty (pre-resolve pipelined messages).
- `refs[host[N-1]][r_T] = RemoteTarget(host[N], r_T_local)`.
- `refs[host[N-2]][p_{N-1}] = RemotePromise(host[N-1], p_{N-1},
  localResolution=<none>)` — and was used to pipeline some
  `op:deliver-only`s sent at `host[N-2]` toward `host[N-1]`.
- `refs[host[N]][r_T_local] = LocalTarget(sink)`.
- `gifts[host[N]]` empty; `nextGiftId[host[N-1]] = 0`.

Step-by-step:

1. **Resolver fires** `ResolverResolve` on `p_{N-1}`. The resolution is
   `RemoteTarget(host[N], r_T_local)` → 3PHO required. Atomically:
   - allocate `giftId = nextGiftId[host[N-1]]`; increment counter.
   - append `op:deposit-gift(giftId, recipient=host[N-2],
     targetLocalRefId=r_T_local, envelope=env)` to
     `channels[host[N-1]][host[N]]`.
   - append `op:resolve(targetRefId=p_{N-1},
     value=desc:handoff-give(gifter=host[N-1], targetHost=host[N],
     giftId, env))` to `channels[host[N-1]][host[N-2]]`.
   - drain `refs[host[N-1]][p_{N-1}].queue` through `host[N-1]`'s
     kind-dispatch (recurse on `r_T` → wire-forward to `host[N]`).
   - mark `refs[host[N-1]][p_{N-1}].resolution = RemoteTarget(host[N],
     r_T_local)`.
2. **`host[N]` receives** `op:deposit-gift`. Installs
   `gifts[host[N]][host[N-1], giftId] = {recipient: host[N-2],
   targetLocalRefId: r_T_local, envelope: env}`.
3. **`host[N-2]` receives** `op:resolve(p_{N-1}, desc:handoff-give(...))`
   via `ReceiveOpResolve_Handoff`. Atomically:
   - mint a fresh local refId `pw` for the withdraw-promise.
   - install `refs[host[N-2]][pw] = RemotePromise(host[N], <opaque
     sentinel>, localResolution=<none>)`. The opacity is captured in the
     opaque sentinel — `host[N-2]` cannot dispatch on the `resolverRefId`
     for anything other than "send to `host[N]`".
   - install `refs[host[N-2]][p_{N-1}].localResolution = pw`. From now
     on, sends on `p_{N-1}` recursively dispatch to `pw`, routing over
     `channels[host[N-2]][host[N]]`. The recipient still does not know
     they're hitting `T` specifically.
   - append `op:withdraw-gift(giftId, gifter=host[N-1],
     withdrawPromiseRefId=pw, env)` to
     `channels[host[N-2]][host[N]]`.
4. **`host[N]` receives** `op:withdraw-gift`. **All atomic, to preserve
   `PairingInvariant`:**
   - look up `gifts[host[N]][host[N-1], giftId]`.
   - **reject** if the slot is empty (`GiftOneShot` violation
     attempt) or `recipient \neq msg.from` (`GiftHasOneRecipient`
     violation attempt); on rejection, drop the message and emit a trace
     marker.
   - otherwise: install `refs[host[N]][pw] = LocalPromise(queue=<empty>,
     listeners={host[N-2]}, resolution=<none>)`. `host[N]` adopts the
     recipient-supplied `pw` refId — both peers thereby share the same
     refId for this withdraw-promise (v0 global-refId convention).
   - resolve `refs[host[N]][pw]` to `LocalTarget(r_T_local)`: the
     listener (`host[N-2]`) is handled via the `LocalTarget`-bypass; a
     direct `op:resolve(pw, desc:remote-target(host[N], r_T_local))` is
     appended to `channels[host[N]][host[N-2]]`. *No nested 3PHO*.
   - clear `gifts[host[N]][host[N-1], giftId] := <<>>` (one-shot
     consumption).
5. **`host[N-2]` receives** `op:resolve(pw, desc:remote-target(host[N],
   r_T_local))` via `ReceiveOpResolve_RemoteTarget`. Installs
   `refs[host[N-2]][pw].localResolution = RemoteTarget(host[N],
   r_T_local)`. Mints (if needed) a fresh `RemoteTarget` entry on
   `host[N-2]` to satisfy the pairing invariant.

### Pipelined-pre-resolve sends

Between steps 1 and 4, `host[N-2]` can pipeline sends on `p_{N-1}` →
they recursively dispatch via `pw` → routed over
`channels[host[N-2]][host[N]]`. The `op:deliver-only` carries `pw` as
its refId; `host[N]` looks up `refs[host[N]][pw]`. *Before* step 4,
that lookup fails (slot not yet allocated) — the message is held
pending receipt of `op:withdraw-gift`. *After* step 4 but before the
queue drains, the message lands in `refs[host[N]][pw].queue` as
ordinary `LocalPromise` queue traffic; step 4's resolve-to-`T_local`
then drains the queue via local shortening.

This matches OCapN reality: pipelined messages on a handed-off ref
*can* reach the target before the recipient has learned the target's
identity, and they're held at the target host as ordinary queued
messages on the target host's local presence for the withdraw-promise.

### Deposit/withdraw FIFO ordering

The deposit (`op:deposit-gift`) is sent on
`channels[host[N-1]][host[N]]`. The recipient's eventual
`op:withdraw-gift` lands on `channels[host[N-2]][host[N]]`. These are
*different* wires, so per-pair FIFO does **not** guarantee the deposit
arrives before the withdraw. The spec explicitly orders them via the
`ReceiveOpWithdrawGift` precondition: it blocks until
`gifts[self][gifter, giftId] /= <<>>`, naturally serializing on the
deposit.

## 8. Subscribe-to-already-resolved

When `op:listen(subscriber, refId)` arrives at `h` and
`refs[h][refId].resolution /= <none>`:

- Immediately reply with the same `op:resolve(refId, value)` the
  resolver would have sent when it first resolved:
  - `value = desc:remote-target(...)` if the resolution is a
    `LocalTarget` on `h` (bypass case).
  - Fresh 3PHO triplet (`op:deposit-gift` to target host plus
    `op:resolve(..., desc:handoff-give(...))` to `subscriber`,
    consuming a fresh `nextGiftId[h]`) if the resolution is a
    `RemoteTarget`.

The handler does not retroactively insert `subscriber` into the
`listeners` set, since the resolution event is one-shot and already
fired. If `refs[h][refId].resolution = <none>`, the handler instead
adds `subscriber` to `refs[h][refId].listeners` for future
notification.

## 9. `op:flush` — resolver-initiated, pushes upstream

Triggered when a `LocalPromise pa` at resolver `H` is about to fire
`op:resolve(targetRefId, R')` for some `R' \in Target`. Before the
notification is queued:

1. `H` enumerates listeners `pa.listeners`.
2. For each `L_i`, `H` appends `op:flush(refId)` to `channels[H][L_i]`
   and marks `pa.flushing = TRUE`.
3. `L_i` receives `op:flush(refId)`. `L_i` marks its `RemotePromise`
   entry for `(H, refId)` as `flushing` — `RoutePromise(L_i, refId)`
   continues to dispatch on the un-flushed `RemotePromise` route while
   `flushing` is true (i.e., sends still go to `H`).
4. `L_i` waits until `Len(channels[L_i][H]) = 0` of any
   `op:deliver-only` whose target is the resolving ref.

   **Cheap-but-conservative** v0 choice: drain *all* of
   `channels[L_i][H]`. Equivalent for our linear chains where ref-1
   traffic dominates. A ref-scoped drain is a tractable future
   refinement.
5. `L_i` appends `op:flush-ack(refId)` to `channels[L_i][H]`.
6. `H` receives `op:flush-ack(refId)` from every `L_i`.
7. `H` drains `pa.queue` through its own kind-dispatch (which may
   include local shortening into the resolution).
8. **Optional drain of `channels[H][R'.targetPeer]`.** If `R'` is a
   `RemoteTarget` on `T_host \neq H`, `H` should additionally wait
   until `Len(channels[H][T_host]) = 0` of `op:deliver-only` whose
   refId resolves to `pa` (or, cheaply, until that channel is fully
   empty of pre-handoff forwards for this ref). Without this, a
   pipelined pre-resolve forward already sitting on
   `channels[H][T_host]` could race the recipient's later
   `op:withdraw-gift` arrival. **Default v0 choice: yes — drain that
   channel of any ref-1 `op:deliver-only` before step 9.**
9. For each `L_i`, `H` allocates a fresh `giftId`, deposits the gift at
   `R'.targetPeer` (`op:deposit-gift` setting
   `gifts[R'.targetPeer][H, giftId] = {recipient: L_i, ...}`), and
   appends `op:resolve(L_i's-refId-for-pa,
   desc:handoff-give(gifter=H, targetHost=R'.targetPeer, giftId, env))`
   to `channels[H][L_i]`. Clears `pa.flushing`. From here the 3PHO
   withdraw round-trip (steps 3-5 of §7) plays out.

The point: by step 6, no `op:deliver-only` traffic from any listener
for `pa` is in flight on any wire to `H`; combined with step 7's drain
of `pa.queue` and step 8's drain of the H→target channel, when each
`L_i` switches to the new route at step 9 nothing can race it via the
old route.

## 10. `EJavaFlush` — subscriber-initiated, holds install on receive

Triggered when subscriber `L` receives `op:resolve(L's-refId-for-pa,
desc:handoff-give(gifter=H, targetHost, giftId, env))` from `H` and
was already pipelining on `(H, refId)`:

1. `L` does **not** immediately install `entry.localResolution = pw`.
2. `L` sets a per-entry `embargo` flag; new sends on `(H, refId)`
   continue on the un-embargoed `RemotePromise` route (still going to
   `H`).
3. `L` waits for its subscriber-local signal — *for the canonical
   (kpreid-realistic) variant*: `Len(channels[L][H]) = 0` of any
   `op:deliver-only` to `H`.
4. `L` mints the withdraw-promise `pw`, installs
   `entry.localResolution = pw`, sends `op:withdraw-gift(giftId,
   gifter=H, pw, env)` to `targetHost`, clears `embargo`. The
   withdraw round-trip then proceeds as in §7.

What subscriber-local signal is `L` allowed to use? The canonical
kpreid-realistic answer is condition (3). Earlier iterations modelled an
`EJavaFlushGlobal` god-view control variant — `L`'s install waits until
*no* `op:deliver-only` on `refId` exists anywhere on the network, an
omniscient signal no real implementation can compute. That variant was
useful as a passing baseline contrasting with the local-signal violation,
but is **dropped in this iteration** to avoid restating its predicates
against the new (post-1c) race surface. The intuition is recorded here:
the omniscient signal is what the realistic local-only signal is missing,
and that gap is exactly what produces the kpreid race in the canonical
`EJavaFlush_4Chain` MC.

## 11. Worked example trace (4-chain, both flush protocols)

Chain: `HeadPeer → p_1@host[1] → p_2@host[2] → p_3@host[3] → T@host[4]`.

Under terminal-only propagation only one `op:resolve` ever fires — the
one from `host[3]` to `host[2]` carrying `T@host[4]`. Only `host[2]` can
shorten in this iteration. The race is between:

- **Old path** `host[2] → host[3] → host[4]`: pre-resolve
  `op:deliver-only`s from `host[2]` (forwarded from upstream) sitting on
  `channels[host[2]][host[3]]`, eventually reaching `host[4]` via
  `channels[host[3]][host[4]]`.
- **New path** `host[2] → host[4]`: post-resolve sends from `host[2]`
  routing via the installed `localResolution` directly to `host[4]` on
  `channels[host[2]][host[4]]`.

**`OpFlushProtocol` (resolver-initiated):** `host[3]` sends
`op:flush(p_2)` to `host[2]`. `host[2]` drains
`channels[host[2]][host[3]]` of its ref-1 backlog, sends `op:flush-ack`
back. `host[3]` also drains `channels[host[3]][host[4]]` of any of its
forwarded ref-1 backlog. Only then does `host[3]` deposit the gift at
`host[4]` and send the `op:resolve(p_2, desc:handoff-give(...))` to
`host[2]`. `host[2]`'s subsequent pipelined sends on the new path strictly
follow all old-path traffic. **FIFO preserved.**

**`EJavaFlush` (subscriber-initiated, canonical local signal):**
`host[3]` immediately deposits the gift and fires `op:resolve(p_2,
desc:handoff-give(...))` to `host[2]`. `host[2]` embargoes the install
and waits for `channels[host[2]][host[3]]` to drain. Once drained,
`host[2]` mints `pw`, installs `localResolution`, fires `op:withdraw-gift`
to `host[4]`. But — and this is the kpreid race — pre-resolve sends from
`host[2]` may still be in flight on `channels[host[3]][host[4]]`
(forwarded by `host[3]` *before* `host[3]`'s resolve fired). New
post-resolve sends from `host[2]` go via the new path
`channels[host[2]][host[4]]`. The two-FIFOs-into-host[4] structure
reorders. **FIFO violated.**

## 12. Open questions / future work

- **Per-peer refId namespaces.** As noted in §1, the v0 model uses a
  global refId convention. The translation to per-peer namespaces is
  mechanical but adds complexity (per-pair refId map state) without
  changing any of the protocols described here.
- **Ref-scoped flush drainage.** The cheap whole-channel-empty
  precondition (§9 step 4, §10 step 3) over-drains. A ref-scoped check
  is a tractable optimization but the v0 spec keeps the simpler form.
- **Distributed P2P shortening.** Each chain node propagating what it
  learned from its downstream (`op:listen` further upstream, sending
  `op:resolve` to its own listeners). Enabled by Phase 1c's
  `RemotePromise.localResolution`, deferred to the next iteration.
- **Multi-sender FIFO testing.** `EndToEndRefFIFO` is already
  per-`(sender, ref)`; multi-sender scenarios fall out naturally once
  handoff produces multiple ref holders, but we won't write MCs for
  them here.
